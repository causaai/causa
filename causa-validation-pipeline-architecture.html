Orchestrated by DiagnosticServiceImpl.runPipelineAsync() — fully asynchronous; HTTP response returns immediately with the PENDING diagnostic.

Pipeline Stages
1
Alert Intake AlertService → DiagnosticServiceImpl

An inbound alert (namespace + pod + container) triggers triggerDiagnostics(alert). A new Diagnostic record is persisted as PENDING and immediately returned to the caller. All subsequent work runs on an async thread pool.

Alert domain object Diagnostic ID (PENDING)
2
Context Collection McpContextCollector → DiagnosticContext

McpContextCollector.collectContext(alert) fans out to multiple data sources and populates a DiagnosticContext value object. The context is serialized via DiagnosticContext.toString() into a labeled, section-structured string consumed by the LLM prompt.

Evidence Fetched — by Source
  • Kubernetes API — pod status, events, current & previous container logs, termination reason, exit codes
  • Kruize — cost recommendations, performance recommendations (memory limit increase signals)
  • Cryostat / JFR — GC analysis, memory analysis, thread analysis, exception analysis, container analysis
  • Quarkus metrics endpoint — raw JVM metrics (GC pause sum, pause max, uptime, heap used/committed)
  • Liberty logs / filesystem — Liberty server logs (VM-platform deployments)
  • JMX / heap dumps — heap status, GC activity, thread state, GC pressure analysis, memory-leak indicators, thread contention, JVM runtime info
DiagnosticContext (structured) contextString (LLM-formatted)
3
LLM Root-Cause Analysis RcaPromptBuilder → PromptSender → RootCauseAnalysis

RcaPromptBuilder constructs a system prompt and a user prompt embedding the full contextString. The prompt is sent to the configured LLM (IBM BOB / Granite / Anthropic / Ollama). The response is parsed into a RootCauseAnalysis JSON record and validated with Bean Validation.

Evidence Used — inside the LLM prompt
  • All labeled sections of the DiagnosticContext string (Kubernetes, Kruize, Cryostat, Quarkus, JMX)
  • Pod events, termination reasons, exit codes — directly embedded as text sections
  • GC/memory/thread analyses from Cryostat — embedded verbatim
  • Raw Quarkus metrics — embedded as key-value metrics block
RootCauseAnalysis anomalyType (e.g. OOM_KILLED, POSSIBLE_GC_PAUSE) rootCause, issueDescription, technicalDescription, possibleSolutions
4
Dual Validation RcaValidatorImpl

RcaValidatorImpl.validate(rca, contextString) drives two independent validation paths in parallel, then aggregates their verdicts. The diagnostic status transitions to VALIDATING before this stage.

PATH A — LLM Assertion Analysis
  • AssertionExtractor — extracts discrete, typed assertions from rca.rootCause()
  • Two implementations:
    • • LlmAssertionExtractor — sends text to LLM with a prompt template; parses JSON assertion DTOs; falls back to sentence splitting on error
    • • SimpleAssertionExtractor — splits on sentence punctuation; classifies by keyword heuristics (causal, trend, config, recommendation)
  • Assertions capped at MAX_ASSERTIONS_PER_VALIDATION to limit LLM cost
  • AssertionAnalyzer (LlmAssertionAnalyzer) — sends each assertion + full contextString to LLM; concurrent via CompletableFuture; parses status, confidence, and evidence snippets from the JSON response
  • Fallback path: ContextBasedEvidenceMatcher — regex-based evidence extraction from contextString (no LLM needed)
  • Recommendations always skip to UNKNOWN
PATH B — Deterministic Rule Engine
  • DiagnosticContextSignalExtractor — regex-parses contextString into typed Signal objects (no LLM)
  • RuleEngine — loads YAML rule set matched to anomalyType:
    OOM_KILLED → oom-killed.yaml
    POSSIBLE_GC_PAUSE → gc-pause.yaml
  • Rules categorized as REQUIRED, SUPPORTING, EXCLUSION
  • Score = required-passed + supporting-passed + exclusion-passed (exclusions carry negative weights)
  • Status: fails instantly if any required rule fails; otherwise scored against minSupported / minPartial thresholds
  • Confidence mapped: Supported→0.8–1.0, Partial→0.5–0.79, Unsupported→0.0–0.49
Evidence Fetched — Path A (LlmAssertionAnalyzer)
  • Each assertion is analyzed against the full contextString via LLM prompt
  • LLM response includes EvidenceDto[]: snippet, source label, relevance score (0–1), evidence type
  • Snippets classified as SUPPORTING evidence (status=supported/partial) or REFUTING (status=unsupported)
  • Evidence types: KUBERNETES_EVENT, POD_LOG, METRIC, KRUIZE_RECOMMENDATION, CRYOSTAT_ANALYSIS, GC_ANALYSIS, MEMORY_ANALYSIS, THREAD_ANALYSIS, EXCEPTION_ANALYSIS, OTHER
Evidence Fetched — Path A Fallback (ContextBasedEvidenceMatcher)
  • OBSERVATION assertions → scans for OOMKilled text, pod status, restart count patterns in context sections
  • TREND assertions → requires ≥2 metric values; scans JFR/memory/Cryostat sections for heap trends
  • CAUSALITY assertions → combines OOMKilled + heap-trend evidence
  • CONFIGURATION assertions → scans for memory-limit values
  • All types also receive keyword-match evidence from assertion text (≥2 non-stop-words match a context line)
  • Relevance scores: OOMKilled=0.95, pod-status=0.90, memory-limit=0.90, heap-trend=0.85, restart=0.85, memory-trend=0.80
Evidence Fetched — Path B (DiagnosticContextSignalExtractor)
  • Kubernetes events → reason field, OOMKilled detection, rollout activity, eviction pressure
  • Container status → exit code (137 → OOMKilled even if Kubernetes says generic error), termination reason
  • Pod status → phase, CrashLoopBackOff detection
  • Metrics → memory trend (increasing/stable), heap % used, after-GC ratio, restart-derived pressure, Quarkus heap
  • Log patterns → OOM errors, full-GC count, GC pause max/total, heap-after-GC ratio, increasing heap from verbose GC
  • Quarkus GC metrics → total GC pause % = pause-sum / process-uptime × 100
  • Kruize recommendations → detects "increase memory limit" language in recommendations
List<ValidationResult> (Path A) HypothesisValidationResult (Path B)
5
Verdict Aggregation ValidationAggregator → DualValidationResult

ValidationAggregator.aggregate() combines Path A and Path B verdicts using one of four configurable strategies. Default is WEIGHTED_AVERAGE (40% assertion / 60% rule-based).

6
Persistence & Summary DiagnosticServiceImpl → DiagnosticRepository

updateDiagnosticWithValidation() serializes the final verdict, assertion results, and rule-based results into JSON and persists a completed Diagnostic. ValidationSummarizer optionally generates a natural-language summary via LLM. The alert is marked processed.

Persisted Validation Fields
  • validation_result — SUPPORTED / PARTIALLY_SUPPORTED / UNSUPPORTED
  • is_valid, overall_confidence — derived from DualValidationResult.FinalVerdict
  • dual_validation — full JSON: assertionBasedVerdict, ruleBasedVerdict, finalVerdict
  • assertion_results — per-assertion status, confidence, supporting/refuting evidence snippets
  • validation_summary — LLM-generated or deterministic fallback narrative

Assertion Types & Classification
Type Meaning Classification Trigger Evidence Strategy (Fallback Matcher)
OBSERVATION Factual state observed in telemetry Default — no keyword match OOMKilled pattern, pod status, restart count
TREND A metric value increasing or decreasing over time trend keywords: increasing, growing, rising… Requires ≥2 memory or heap values from metrics sections
CAUSALITY Causal relationship between two events causal keywords: caused, led to, resulted in, triggered… OOMKilled evidence + heap-trend evidence combined
CONFIGURATION A configuration setting contributing to the issue config keywords: limit, threshold, setting, configured… Memory limit value extraction from config sections
RECOMMENDATION Suggested action to remediate the issue Source = POSSIBLE_SOLUTIONS or recommendation keywords Skipped — automatically UNKNOWN
Key Domain Objects
ClassRoleKey Fields
